## Что и как копируется

| Задача | Источник | Когда | Хранение |
|---|---|---|---|
| `ca` | PKI удостоверяющего центра | ежесуточно 03:20 | 14 суточных + 8 недельных |
| `vpn` | Сертификаты, ключи и конфигурация VPN-сервера | ежесуточно 03:20 | 14 суточных + 8 недельных |

Цепочка каждого запуска:

1. **Архив** источников с проверкой минимального размера. Архив меньше порога
   означает, что в него попала пустая точка монтирования — формально успех,
   фактически копии нет.
2. **Шифрование** GPG AES-256 **до** отправки. Незашифрованный архив сразу
   стирается через `shred`.
3. **Передача** на `backup-server` по SSH выделенным ключом.
4. **Сверка контрольной суммы** SHA-256 на приёмной стороне. Без неё мы знали
   бы лишь, что `scp` не вернул ошибку, а не что данные доехали целыми.
5. **Ротация**: последние 14 копий всегда, из более старых — только
   воскресные, не больше 8.
6. **Метрики** для Prometheus — при **любом** исходе, включая провал.

Почему шифрование до отправки обязательно: копия центра содержит его
приватный ключ. Незашифрованная копия на чужом диске — полная компрометация
системы доверия: злоумышленник выпустит себе любой сертификат, и отличить его
от легитимного будет невозможно.

## Проверка на практике

### Копирование

```
[INFO ] Создаю архив задачи ca
[INFO ] Размер архива: 12258 байт
[INFO ] Шифрую копию
[INFO ] Отправляю на 10.129.0.10
[OK   ] Копия доставлена и проверена по контрольной сумме
[INFO ] Убираю устаревшие копии
[OK   ] Копирование задачи ca завершено успешно (12354 байт)
```

Для VPN-сервера аналогично, 11144 байт.

### Восстановление

Копия, которую ни разу не пробовали развернуть, — это не резервная копия, а
надежда. Поэтому проверка восстановления важнее самого копирования.

```
[INFO ] Беру самую свежую копию: ca-20260921-085540.tar.gz.gpg
[INFO ] Сверяю контрольную сумму
[OK   ] Целостность подтверждена
[INFO ] Расшифровываю
[INFO ] Распаковываю
[INFO ] Проверяю содержимое копии
Enter pass phrase for .../pki/private/ca.key:
[OK   ] Копия корректна: корневой сертификат + ключ, выпущено сертификатов: 2
[OK   ] Копия проверена: расшифровывается, распаковывается, содержимое на месте
[INFO ] Временные данные удалены
```

Запрос парольной фразы здесь — полезное свойство, а не помеха. Чтобы
убедиться, что ключ и сертификат центра составляют пару, из ключа надо
извлечь открытую часть, а для этого — расшифровать его. Выходит, что проверка
подтверждает заодно и то, что **фраза не утеряна**. Копия зашифрованного ключа
без фразы бесполезна, и этот сценарий обычно обнаруживается в худший момент.

Расшифрованные данные после проверки удаляются: приватные ключи не должны
оставаться на диске.

## Уровни хранения — без преувеличений

| Уровень | Состояние |
|---|---|
| `backup-server` в зоне `ru-central1-b`, данные в `ru-central1-a` | работает |
| Снимки дисков по расписанию `infra-daily` | работает |
| Объектное хранилище Yandex | подготовлено, не включено |

Копии физически находятся в другом дата-центре, чем данные. У сервера
хранения нет публичного адреса — доступ только из внутренней сети.

Объектное хранилище не включено сознательно: для него нужен сервисный аккаунт
и статические ключи доступа — ещё один секрет, требующий хранения и ротации.
Код отправки есть в `backup.sh`, включение — правка двух строк в
`backup.conf`. Вынесено в план развития.

### Хранение скриптов и пакетов

Ответ на пункт 4 задания — **этот репозиторий**. Исходники, собранные пакеты
в `dist/`, документация; каждый блок — отдельный коммит с объяснением
изменений. Hosted-сервис выбран сознательно: собственный Git-сервер стал бы
ещё одним объектом, требующим защиты, мониторинга и бэкапа, — об этом
предупреждает пункт 5 задания.

Бонусный пункт 5 (собственный deb-репозиторий) не выполнен: для четырёх машин
установка из `dist/` работает, а репозиторий добавил бы ещё один сервис.

## Односторонность доверия

Ключи доступа к серверу хранения прописываются **вручную**, скрипт настройки
не делает этого сам. Это осознанно: машина-источник не должна иметь права
записи в `authorized_keys` на хранилище. Иначе скомпрометированный сервер смог
бы добавить себе доступ или удалить чужой, а вместе с ним — и копии.

## Дефекты, найденные при развёртывании

Все четыре дефекта этого блока обнаружились только на живой инфраструктуре.
Ни shellcheck, ни lintian, ни ручной запуск скриптов из терминала их не
показывали.

### У служб systemd нет переменной `HOME`

Копирование по расписанию падало с `HOME: unbound variable`. Файл
`project.env` строил путь к ключу через `${HOME}`, а у служб systemd эта
переменная не задана. Строгий режим `set -u` превращал обращение к ней в
аварийный выход. Из терминала `HOME` есть — поэтому ручной запуск всё
показывал исправным.

**Решение:** `${HOME:-/root}` в `project.env` и `Environment=HOME=/root` в юните.
Заодно выяснилось, что `backup.sh` не использует **ни одной** переменной из
`project.env`, — строка `source` была лишней точкой отказа и убрана.

### Мониторинг не видел сбой — главная находка блока

Копирование не работало **семнадцать часов**, а мониторинг молчал. Две причины
сложились вместе.

Скрипт падал при чтении `project.env` — **до** установки ловушки, пишущей
метрики при любом выходе. Метрики о сбое не записывались вовсе.

А оба алерта считались по метрикам. `BackupTooOld` вычисляет
`time() - infra_backup_last_success_timestamp_seconds`; если метрики нет,
результат пустой и сравнивать не с чем. `BackupFailed` смотрит на код
возврата, которого тоже нет. Оба молчат ровно тогда, когда метрик нет.

**Решение:** лишний `source` убран, а в правила добавлен
`BackupNeverSucceeded` через `absent()` — функцию, срабатывающую именно на
**отсутствие** метрики.

Общий вывод, применимый далеко за пределами этой работы: алерт, считающийся
по метрике, молчит, когда метрики нет. К каждому «что-то пошло не так» нужен
парный алерт «ничего не происходит».

Формально пункт 7 задания был выполнен и до исправления: метрики, алерты — всё
на месте. Фактически мониторинг не замечал отсутствия копий. Разница между
«настроено» и «работает» проявилась только на практике.

### Системный пользователь `backup` уже существует

После прописывания ключей сервер по-прежнему отвечал `Permission denied`.
Причина: в Debian и Ubuntu пользователь `backup` — **системный**, из базового
пакета:

```
backup:x:34:34:backup:/var/backups:/usr/sbin/nologin
```

Команда `useradd ... backup 2>/dev/null || true` молча провалилась.
Пользователь остался с домашним каталогом `/var/backups` — `sshd` искал
ключи там, а не в `/srv/backups`. Оболочка `nologin` не пустила бы и с
правильным ключом.

**Решение:** пользователь хранилища переименован в `infra-backup`, а создание
идёт через явную проверку `getent passwd`, без подавления ошибок.

Конструкция `2>/dev/null || true` выглядит безобидно — «если пользователь уже
есть, ничего страшного». Но она скрыла, что пользователь есть **с другими
свойствами**. Скрипт отработал «успешно», а проблема проявилась тремя шагами
позже, в другом месте и с сообщением, указывающим не туда. Подавлять ошибку
стоит, только когда точно известно, какая именно ошибка ожидается.

### Сообщение об ошибке указывало не туда

При отказе в доступе скрипт писал «Сервер бэкапов недоступен». Сервер был
доступен — он не принимал ключ. Это разные ситуации, и лечатся они по-разному.

**Решение:** скрипт различает три случая — сервер не отвечает, ключ не принят,
у пользователя нет оболочки, — и для каждого даёт конкретную подсказку.
