## Ключевое решение: приватный ключ не покидает машину владельца

Рекомендация 3 к этому блоку сформулирована прямо: клиент передаёт администратору только CSR. Схема выстроена вокруг этого.

```
Сотрудник                Администратор              Центр            VPN-сервер
    │                                                                      
 gen-client-request.sh                                                     
    │  создаёт ключ + CSR                                                  
    ├──── только .req ────────>│                                           
    │                          │  сверяет отпечаток                        
    │                          ├──── .req ─────────>│                      
    │                          │                  подпись                  
    │                          │<──── .crt ────────┤                       
    │                          ├──────────── .crt ──────────────>│         
    │                          │                            сборка комплекта
    │<──── bundle.tar.gz ──────┤<───────────────────────────────┤         
 assemble-config.sh                                                        
    │  вшивает СВОЙ ключ → .ovpn                                           
```

Приватный ключ не пересекает ни одну стрелку. Следствие: компрометация удостоверяющего центра не раскрывает ключи сотрудников — их там физически нет. Архив с комплектом можно передавать обычной почтой, без ключа получателя он бесполезен.

Отпечаток запроса сверяется по независимому каналу. Это единственная защита от подмены CSR по дороге, и `issue-client-cert.sh` требует подтверждения, прежде чем подписывать.

## Конфигурация сервера: что и почему

| Директива | Причина выбора |
|---|---|
| `proto udp` | Туннелирование TCP внутри TCP даёт наложение таймаутов повтора, и на плохой связи скорость обваливается. Сотрудники работают через публичный Wi-Fi |
| `tls-crypt` | Шифрует само TLS-рукопожатие. Пакет без общего ключа отбрасывается молча — сканер портов не видит, что на 1194/udp что-то есть |
| `dh none` | Ключи на эллиптических кривых, обмен по ECDH. Параметры Диффи-Хеллмана не нужны |
| `cipher AES-256-GCM` | Режим с встроенной проверкой подлинности: шифрует и гарантирует неизменность пакета |
| `remote-cert-tls client` | Сотрудник с клиентским сертификатом не сможет выдать себя за сервер для другого сотрудника |
| `crl-verify` | Сертификат уволившегося перестаёт работать сразу, не дожидаясь истечения срока |
| `push "redirect-gateway"` | Заворачивает **весь** трафик клиента в туннель. Без неё туннель поднимется, но внешний адрес не изменится |
| `user nobody` | Успешная атака на демон даёт права `nobody`, а не root |
| `topology subnet` | Обычный адрес с маской /24 вместо устаревшей схемы net30 |

Директива `duplicate-cn` намеренно **не включена**. Каждому устройству выдаётся свой сертификат, поэтому два подключения с одинаковым Common Name означают, что сотрудник передал кому-то свой ключ. Пусть второе подключение рвёт первое — это заметно и приводит к разбирательству.

## Три дефекта, найденных до развёртывания

Конфигурация была перечитана на предмет того, что выстрелит уже на сервере. Каждый из этих случаев стоил бы часов отладки.

### Список отзыва был недоступен после понижения привилегий

OpenVPN перечитывает CRL при **каждом** подключении клиента — то есть уже от имени `nobody`. Файл лежал в `/etc/openvpn/server` с правами `0700 root:root`, куда `nobody` не может даже войти.

Картина отказа особенно неприятная: служба стартует, `systemctl status` показывает `active`, в журнале ни слова — а все клиенты получают отказ.

Решение: CRL вынесен в `/etc/openvpn/crl.pem` с правами `0644`. Секрета в нём нет, это список серийных номеров. В `verify.sh` добавлена прямая проверка `sudo -u nobody test -r`.

### `push "block-outside-dns"` ломал не-Windows клиентов

Директива существует только в клиенте под Windows. Клиент на Linux или macOS, получив её от сервера, завершается с `Options error: --block-outside-dns requires Windows`.

Поскольку шаблон клиентской конфигурации один на все платформы, директива убрана с сервера. Windows-клиентам она добавляется в их `.ovpn` вручную.

### Список отзыва не проверялся на срок

Просроченный CRL заставляет OpenVPN отвергать **всех** клиентов. Авария выглядит как «никто не может подключиться», хотя ни один сертификат не истёк. Теперь `setup-vpn-server.sh` проверяет срок перед запуском службы.

## Два дефекта, найденных при развёртывании

### Common Name сертификата оказался `ChangeMe`

В журнале клиента обнаружилось `Peer Connection Initiated with [ChangeMe]` вместо `[vpn-server]`.

Причина тонкая: в команде `easyrsa gen-req vpn-server` имя задаёт только **имена файлов**, а Common Name берётся из переменной `EASYRSA_REQ_CN`. В интерактивном режиме его спрашивают у оператора, но с флагом `--batch` подставляется значение по умолчанию из Easy-RSA.

На работу это не влияло: клиент проверяет подпись центра и расширение сертификата, а не имя. Но сертификат должен корректно идентифицировать сервер.

Исправлено: переменная задаётся явно, а результат сразу проверяется — молчаливая подстановка чужого значения обнаруживается на месте.

**Попутная польза.** Перевыпуск потребовал пройти процедуру отзыва целиком: `easyrsa revoke`, обновление CRL, перенос на сервер, пересборка клиентского комплекта. В `pki/index.txt` остался след — строка `R` для отозванного сертификата рядом с действующим. Это закрывает пункт 9 задания на практике, а не на словах.

### `mute 20` прятал важные строки журнала

Директива подавляла в том числе `Initialization Sequence Completed` — канонический признак успешного подключения.

На сервере подавление уместно, журнал растёт годами. У клиента сеанс короткий, и прятать нечего. Убрано из шаблона.

## Проверка артефактов на отдельной ВМ (пункт 7)

Скрипт [`test-on-fresh-vm.sh`](../../scripts/test/test-on-fresh-vm.sh) создаёт временную машину, проверяет пакеты и удаляет её. Проверять на рабочем сервере бессмысленно: там уже разрешены зависимости и созданы каталоги, и половина проблем не проявится.

| Проверка | Результат |
|---|---|
| Установка на чистую систему | Все пакеты, зависимости разрешены из репозиториев |
| Состояние пакетов | Шесть в состоянии `install ok installed` |
| Коды возврата команд | `infra-ca-sign` и `infra-vpn-make-client` без аргументов → 64 (EX_USAGE) |
| Man-страницы | Все четыре на месте |
| Права на каталоги с ключами | `/var/lib/infra-ca` и `/var/lib/infra-vpn` — 700 |
| Повторная установка | Установочные сценарии отрабатывают повторно без ошибок |
| Полная очистка | Система возвращается к исходному состоянию |

Прогон вскрыл дефект в самом пакете мониторинга: он приносил `/etc/prometheus/prometheus.yml`, принадлежащий пакету `prometheus`, и установка прерывалась. Исправлено переименованием собственных конфигураций и переопределением службы через drop-in для systemd. Тот же приём применён в `infra-node-metrics` для `/etc/default/prometheus-node-exporter`.

Заодно исправлены четыре дефекта самого проверочного скрипта, включая опасный: `infra-ca-init` действительно разворачивала удостоверяющий центр на тестовой машине, потому что запускалась без аргументов от root. Теперь команды без обязательных аргументов проверяются иначе — наличием, исполняемостью и синтаксисом.

## Изменения в артефактах блока 1

По ходу работы исправлены дефекты, обнаруженные при развёртывании:

| Что | Причина |
|---|---|
| `yc_exists` переписана, убрано переопределение `IFS` | `IFS=$'\n\t'` ломал разделение слов, проверка существования ресурса всегда отвечала «нет», и скрипты не были идемпотентными |
| Правила групп безопасности | У `yc` требования к портам противоположны: `protocol=any` их требует, `protocol=icmp` запрещает |
| Убран `--format table` | Флаг не поддерживается, табличный вывод и так по умолчанию |
| Резервируется два статических адреса вместо трёх | Серверу мониторинга достаточно эфемерного, квота не расходуется |
| Обращения к каталогу центра через `sudo` | Каталог имеет права `0700 root:root`, и `scp` от обычного пользователя в него не входит |
| `infra-ca-init`: линкуются все файлы Easy-RSA | Без `openssl-easyrsa.cnf` и `x509-types` команда `build-ca` падала |
| `infra-node-metrics`: drop-in вместо чужого конфига | Пакет приносил `/etc/default/prometheus-node-exporter`, принадлежащий другому пакету |

Версии пакетов подняты, изменения записаны в `debian/changelog`.
