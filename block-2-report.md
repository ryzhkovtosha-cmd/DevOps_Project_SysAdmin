## Ключевое решение: приватный ключ не покидает машину владельца

Рекомендация 3 к этому блоку сформулирована прямо: клиент передаёт администратору только CSR. Схема выстроена вокруг этого.

```
Сотрудник                Администратор              Центр            VPN-сервер
    │                                                                      
 gen-client-request.sh                                                     
    │  создаёт ключ + CSR                                                  
    ├──── только .req ────────>│                                           
    │                          │  сверяет отпечаток                        
    │                          ├──── .req ─────────>│                      
    │                          │                  подпись                  
    │                          │<──── .crt ────────┤                       
    │                          ├──────────── .crt ──────────────>│         
    │                          │                            сборка комплекта
    │<──── bundle.tar.gz ──────┤<───────────────────────────────┤         
 assemble-config.sh                                                        
    │  вшивает СВОЙ ключ → .ovpn                                           
```

Приватный ключ не пересекает ни одну стрелку. Следствие: компрометация удостоверяющего центра не раскрывает ключи сотрудников — их там физически нет. Архив с комплектом можно передавать обычной почтой, без ключа получателя он бесполезен.

Отпечаток запроса сверяется по независимому каналу. Это единственная защита от подмены CSR по дороге, и `issue-client-cert.sh` требует подтверждения, прежде чем подписывать.

## Конфигурация сервера: что и почему

| Директива | Причина выбора |
|---|---|
| `proto udp` | Туннелирование TCP внутри TCP даёт наложение таймаутов повтора, и на плохой связи скорость обваливается. Сотрудники работают через публичный Wi-Fi |
| `tls-crypt` | Шифрует само TLS-рукопожатие. Пакет без общего ключа отбрасывается молча — сканер портов не видит, что на 1194/udp что-то есть |
| `dh none` | Ключи на эллиптических кривых, обмен по ECDH. Параметры Диффи-Хеллмана не нужны |
| `cipher AES-256-GCM` | Режим с встроенной проверкой подлинности: шифрует и гарантирует неизменность пакета |
| `remote-cert-tls client` | Сотрудник с клиентским сертификатом не сможет выдать себя за сервер для другого сотрудника |
| `crl-verify` | Сертификат уволившегося перестаёт работать сразу, не дожидаясь истечения срока |
| `push "redirect-gateway"` | Заворачивает **весь** трафик клиента в туннель. Без неё туннель поднимется, но внешний адрес не изменится |
| `user nobody` | Успешная атака на демон даёт права `nobody`, а не root |
| `topology subnet` | Обычный адрес с маской /24 вместо устаревшей схемы net30 |

Директива `duplicate-cn` намеренно **не включена**. Каждому устройству выдаётся свой сертификат, поэтому два подключения с одинаковым Common Name означают, что сотрудник передал кому-то свой ключ. Пусть второе подключение рвёт первое — это заметно и приводит к разбирательству.

## Проверка артефактов на отдельной ВМ (пункт 7)

Скрипт [`test-on-fresh-vm.sh`](../../scripts/test/test-on-fresh-vm.sh) создаёт временную машину, проверяет пакеты и удаляет её. Проверять на рабочем сервере бессмысленно: там уже разрешены зависимости и созданы каталоги, и половина проблем не проявится.

| Проверка | Результат |
|---|---|
| Установка на чистую систему | Все пакеты, зависимости разрешены из репозиториев |
| Состояние пакетов | Шесть в состоянии `install ok installed` |
| Коды возврата команд | `infra-ca-sign` и `infra-vpn-make-client` без аргументов → 64 (EX_USAGE) |
| Man-страницы | Все четыре на месте |
| Права на каталоги с ключами | `/var/lib/infra-ca` и `/var/lib/infra-vpn` — 700 |
| Повторная установка | Установочные сценарии отрабатывают повторно без ошибок |
| Полная очистка | Система возвращается к исходному состоянию |
