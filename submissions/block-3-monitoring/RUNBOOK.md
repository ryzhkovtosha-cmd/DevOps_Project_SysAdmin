# Блок 3. Настройка мониторинга

Пошаговый порядок работ с пояснениями. После каждого шага есть проверка —
не переходите к следующему, пока она не прошла.

---

## Главное, что нужно спланировать заранее

Задание требует скриншот с **несколькими днями исторических данных метрик**.
Это единственная часть работы, которую нельзя ускорить: мониторинг надо
развернуть за 3–5 дней до сдачи и оставить машины работать.

Практический план: сегодня развернуть мониторинг, дальше писать документацию
блоков 5 и 6 — она серверов не требует, — а через несколько дней снять
скриншоты графиков.

Из этого следует важное: **машины нельзя останавливать**, включая
`ca-server`. Prometheus опрашивает все четыре, и остановленная машина оставит
дыру на графике и висящий алерт `InstanceDown`.

## Что было исправлено перед развёртыванием

Конфигурация была перечитана под **версии, которые реально стоят в
Ubuntu 20.04**. Нашлись три проблемы, каждая из которых привела бы к отказу
службы при старте.

### Prometheus 2.15 не поддерживает `--web.config.file`

Флаг появился только в версии 2.24 (декабрь 2020). Наш drop-in передавал его
явно — служба отказалась бы стартовать с `unknown flag`.

Заодно это означает, что встроенной аутентификации у Prometheus в Ubuntu 20.04
**нет вообще**. Рекомендация 4 задания — «изучите включение базовой
аутентификации» — с распакованным пакетом дистрибутива невыполнима.

**Решение:** веб-интерфейсы закрыты обратным прокси nginx с `auth_basic`.
Службы слушают только `127.0.0.1`, снаружи запросы приходят на nginx, который
требует пароль. Работает с любой версией и заодно даёт готовую точку для
подключения HTTPS через Let's Encrypt — это рекомендация 3.

Порты не переназначались: Prometheus слушает `127.0.0.1:9090`, nginx —
`10.128.0.12:9090`. Конфликта нет, адреса разные.

### Alertmanager в Ubuntu 20.04 — версии 0.15.3

Это 2018 год. Конфигурация была написана под современный синтаксис, которого
он не понимает:

| Конструкция | Появилась в |
|---|---|
| `matchers:` | 0.22 |
| `source_matchers:` / `target_matchers:` | 0.22 |
| `smtp_auth_password_file` | 0.25 |

**Решение:** переписано на `match` / `source_match` / `target_match_re` —
они работают и в 0.15, и во всех последующих версиях. Пароль SMTP
подставляется скриптом настройки прямо в конфигурацию, а права на файл
ограничиваются до 0640 `root:prometheus`.

Это заметный шаг назад по гигиене секретов, и он вынужденный. В плане развития
переход на свежие версии стоит отдельным пунктом.

### Переопределение `ExecStart` теряло пути дистрибутива

Drop-in переопределял команду запуска целиком. Но в юните стоит
`ExecStart=/usr/bin/prometheus $ARGS`, а пути к хранилищу метрик и шаблонам
консолей **вкомпилированы в сборку дистрибутива**. Переопределив команду, мы
бы их потеряли.

**Решение:** drop-in добавляет второй `EnvironmentFile`. Несколько таких
файлов читаются по порядку, и последний побеждает — наш идёт после штатного
`/etc/default/prometheus` и перекрывает заданную там пустую `ARGS`. Штатная
конфигурация дистрибутива остаётся нетронутой.

## Шаг 1. Создать виртуальную машину

```bash
cd ~/projects/devops-final
tar -xzf ~/Downloads/block3-update.tar.gz

./scripts/cloud/30-create-vm.sh mon
MON_PUBLIC=$(yc compute instance get --name mon-server --format json \
             | grep -oP '"address":\s*"\K[0-9.]+' | tail -1)
echo "mon-server: $MON_PUBLIC"
```

Адрес у этой машины **эфемерный** — это осознанное решение из блока 1. Квота
на статические адреса невелика, а веб-интерфейс открывается через VPN, и
смена адреса ничего не ломает.

**Проверка:**

```bash
until ssh -o ConnectTimeout=10 yc-user@$MON_PUBLIC true 2>/dev/null; do sleep 15; done
echo "доступ есть"
```

## Шаг 3. Настроить сервер мониторинга

```bash
ssh -t yc-user@$MON_PUBLIC 'sudo ~/scripts/monitoring/setup-prometheus.sh'
```

Скрипт интерактивен и спросит два пароля:

1. **Пароль веб-интерфейсов** — им вы будете заходить в Prometheus и
   Alertmanager под пользователем `admin`. Хранится как хеш bcrypt.
2. **Пароль почтового ящика** для отправки писем. Можно пропустить нажатием
   Enter, если почта пока не настроена — всё остальное будет работать.

Оба запишите в менеджер паролей.

Дальше скрипт сам: проверит конфигурацию через `promtool`, настроит прокси,
откроет порты только для вашего адреса и подсети VPN, запустит службы и
убедится, что снаружи запрос возвращает `401`.

**Проверка:**

```bash
ssh yc-user@$MON_PUBLIC 'sudo ~/scripts/test/verify.sh mon'
```

## Шаг 4. Экспортёры на остальных машинах

Пункт 9 задания — «серверы принимают запросы только от Prometheus» — уже
выполнен на двух уровнях: правило в группе безопасности облака и rich rule в
firewalld ограничивают порт 9100 адресом `10.128.0.12/32`.

```bash
for host in $CA_IP $VPN_IP; do
    scp dist/infra-common_*.deb dist/infra-node-metrics_*.deb yc-user@$host:~/
    ssh yc-user@$host 'sudo apt-get install -y ./infra-common_*.deb ./infra-node-metrics_*.deb'
done
```

На VPN-сервере метрики самого OpenVPN собирает команда
`infra-openvpn-metrics` из пакета `infra-vpn-config` версии 1.0.3 — ставить
отдельно ничего не нужно:

```bash
scp dist/infra-vpn-config_1.0.3_all.deb yc-user@$VPN_IP:~/
ssh yc-user@$VPN_IP 'sudo apt-get install -y ./infra-vpn-config_1.0.3_all.deb'
```

Готовый экспортёр `kumina/openvpn_exporter` не используется: его репозиторий
заархивирован, собранных бинарных файлов нет. Собственный сборщик разбирает
файл состояния сервера и отдаёт метрики через textfile-коллектор
node-exporter. Главное в нём — `openvpn_status_update_time_seconds`: зависший
демон остаётся `active` с точки зрения systemd, но перестаёт обновлять
состояние, и эта метрика ловит ровно такой случай.

**Проверка:**

```bash
ssh yc-user@$VPN_IP 'systemctl list-timers infra-openvpn-metrics.timer --no-pager'
ssh yc-user@$VPN_IP 'curl -s http://10.128.0.11:9100/metrics | grep ^openvpn_'
```

## Шаг 5. Убедиться, что данные приходят

```bash
ssh yc-user@$MON_PUBLIC \
  'curl -s "http://127.0.0.1:9090/api/v1/targets" | python3 -m json.tool | grep -E "\"health\"|\"instance\""'
```

Все цели должны быть в состоянии `up`. Если какая-то `down` — проверьте на той
машине, что `prometheus-node-exporter` запущен и порт открыт в firewalld.

Веб-интерфейс через туннель VPN:

```
http://10.128.0.12:9090/targets
```

Подключитесь к своему VPN и откройте адрес в браузере — это же и есть
демонстрация того, что инфраструктура работает как задумано.

## Шаг 6. Проверить алерты

Убедиться, что правила загрузились:

```bash
ssh yc-user@$MON_PUBLIC \
  'curl -s http://127.0.0.1:9090/api/v1/rules | python3 -c "
import json,sys
d=json.load(sys.stdin)[\"data\"][\"groups\"]
print(\"групп:\", len(d), \"правил:\", sum(len(g[\"rules\"]) for g in d))
for g in d:
    print(\" \", g[\"name\"], \"—\", len(g[\"rules\"]))
"'
```

Ожидается 21 правило в пяти группах.

**Вызвать настоящий алерт** — лучшее доказательство работоспособности.
Остановите экспортёр на любой машине и подождите три минуты:

```bash
ssh yc-user@$VPN_IP 'sudo systemctl stop prometheus-node-exporter'
sleep 180
ssh yc-user@$MON_PUBLIC 'curl -s http://127.0.0.1:9090/api/v1/alerts | python3 -m json.tool | head -30'
```

Алерт `InstanceDown` должен перейти в состояние `firing`, а Alertmanager —
отправить письмо. Снимите скриншот и верните на место:

```bash
ssh yc-user@$VPN_IP 'sudo systemctl start prometheus-node-exporter'
```

## Шаг 8. Подождать и снять графики

Через 3–5 дней:

```
http://10.128.0.12:9090/graph
```

Запросы для скриншотов:

| Запрос | Что показывает |
|---|---|
| `node_memory_MemAvailable_bytes` | доступная память по всем машинам |
| `100 - (avg by (instance_name) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100)` | загрузка процессора |
| `node_filesystem_avail_bytes{mountpoint="/"}` | свободное место |
| `openvpn_server_connected_clients` | подключения к VPN |
| `up` | доступность целей |

Установите диапазон 7 дней и включите режим Graph.

## Если что-то не работает

| Симптом | Причина | Проверка |
|---|---|---|
| Служба не стартует | Неизвестный флаг в ARGS | `journalctl -u prometheus -n 30` |
| `401` при локальном curl | Обращаетесь через прокси вместо loopback | Используйте `127.0.0.1:9090` |
| Веб-интерфейс недоступен снаружи | Адрес не в `ADMIN_CIDR` | `curl -s ifconfig.me`, сверить с `sg-mon` |
| Цель `down` | Экспортёр не запущен или порт закрыт | `systemctl status prometheus-node-exporter` на той машине |
| Письма не приходят | Пароль SMTP не подставлен | `grep @@SMTP_PASSWORD@@ /etc/prometheus/infra-alertmanager.yml` |
| Алерты не загрузились | Ошибка в правилах | `promtool check rules /etc/prometheus/rules/*.yml` |
| nginx не стартует | Адрес в конфиге не совпадает с адресом машины | `nginx -t`, сверить `MON_IP` в `project.env` |
