## Что сделано

### Сетевой слой

Создана **собственная** VPC-сеть `infra-net`, а не использована `default`.
В сети по умолчанию оказывается любая ВМ этого облака, включая чужие
эксперименты. Своя сеть даёт изолированный периметр и фиксированную
адресацию, на которую можно опереться в правилах фаервола.

Две подсети в разных геозонах: `ru-central1-a` для основных машин и
`ru-central1-b` под будущее хранилище резервных копий. Копии в том же
дата-центре, что и данные, не защищают от отказа дата-центра.

Четыре группы безопасности по ролям. Для машины центра — `sg-ca`, самая
закрытая: только SSH с адреса администратора и порт экспортёра метрик для
сервера мониторинга. Больше ничего: удостоверяющий центр не обслуживает
сетевых запросов.

### Защита машины

Пакет `infra-hardening` приводит свежесозданную ВМ к принятому состоянию
защищённости:

- **SSH**: запрещён вход под root и по паролю, только ключи; современные
  алгоритмы обмена и шифрования; ограничение попыток и времени сессии.
- **Параметры ядра**: защита от подмены адреса источника (`rp_filter`), от
  SYN-флуда, от навязанных извне маршрутов; игнорирование широковещательных
  пингов.
- **Обновления безопасности** ставятся автоматически, но без автоматической
  перезагрузки: момент выбирает администратор.

Установочный сценарий устроен с двумя предохранителями. Перед отключением
парольного входа он проверяет, что хотя бы у одного пользователя есть
`authorized_keys` — иначе оставляет пароли включёнными и предупреждает.
Перед перезапуском SSH прогоняет `sshd -t`: перезапуск со сломанной
конфигурацией оставил бы машину без доступа.

Отдельная деталь для Ubuntu 20.04: её штатный `sshd_config` не содержит
директивы `Include`, поэтому файлы в `sshd_config.d/` просто не читались бы.
Сценарий добавляет директиву первой строкой и сохраняет копию оригинала для
отката при `purge`.

### Удостоверяющий центр

Команда `infra-ca-init` разворачивает PKI и выпускает корневой сертификат.

Криптография: эллиптические кривые `secp384r1` вместо RSA, хеш SHA-512.
Ключи короче, подпись быстрее, стойкость сопоставима с RSA-3072. Побочный
эффект, который пригодится в блоке 2: не нужны параметры Диффи-Хеллмана.

Сроки: корневой сертификат — 10 лет, выдаваемые — 1 год. Короткий срок
клиентских сертификатов ограничивает окно полезности украденного ключа и
заставляет регулярно сверять список действующих сотрудников.

Сразу создаётся **список отзыва** (CRL). Без него отозвать сертификат
уволившегося было бы невозможно — пришлось бы ждать истечения срока.

Парольная фраза приватного ключа запрашивается интерактивно и **нигде не
сохраняется**. Хранить её в скрипте значило бы обесценить саму защиту ключа.

### Выдача сертификатов

Команда `infra-ca-sign` подписывает присланный запрос. На машину центра
попадает только CSR — приватный ключ получателя создаётся у него и сюда не
передаётся.

Это прямая рекомендация задания, и следствие у неё существенное:
компрометация удостоверяющего центра не раскрывает ключи сотрудников, потому
что их там физически нет.

Проверки перед подписанием: файл действительно является запросом, Common Name
в нём совпадает с указанным именем, сертификат на это имя ещё не выпускался.
Проверка подлинности отправителя остаётся за оператором — отпечаток запроса
сверяется по независимому каналу.

## Ответ на пункт 5 рекомендаций: зашифрованный раздел диска

Задание предлагает решить, нужен ли отдельный зашифрованный раздел для
хранения ключей. **Решение — не создавать.**

Диски в Yandex Cloud шифруются на стороне провайдера, что закрывает сценарий
физического доступа к носителю. LUKS поверх этого защищал бы от доступа к
образу диска через API облака, но на безголовой машине ключ разблокировки
должен где-то лежать. Положить его на ту же машину — значит не защитить
ничего. Держать вне машины — значит потерять автоматическую загрузку после
перезапуска, а перезагрузки в облаке случаются не по нашей воле.

Вместо этого применены меры с реальным эффектом: приватный ключ защищён
парольной фразой, каталог PKI имеет права `0700`, на машине нет ни одного
сетевого сервиса кроме SSH, доступ ограничен адресом администратора, а
резервные копии (блок 4) шифруются до отправки.

## Как проверялось качество

### Соответствие Debian Policy

```
$ lintian dist/*.deb
```

Все четыре пакета проходят **без замечаний**.

По ходу работы `lintian` нашёл и заставил исправить пять настоящих дефектов:
`coreutils` в `Depends` (это essential-пакет), shebang у библиотеки, которая
только подключается через `source`, прямые вызовы `systemctl` вместо
`deb-systemd-invoke`, рекурсивный `chown -R` (идёт по символическим ссылкам,
и подложенная ссылка сменила бы владельца чужому файлу) и вызов команды по
полному пути в `postinst`. Для всех четырёх команд в `/usr/sbin` написаны
man-страницы — Debian Policy этого требует.

Одно замечание отфильтровано как **ложное**:
`description-synopsis-is-duplicated` срабатывает на `infra-hardening`, хотя
синопсис и первая строка описания у него разные. Проверено контрольным
экспериментом: тот же текст латиницей замечаний не даёт, кириллицей — даёт.
Это дефект парсера lintian, а не пакета.

### Качество скриптов

```
$ shellcheck -x -S warning scripts/*/*.sh packages/*/usr/sbin/*
```

Замечаний нет. Все скрипты используют строгий режим `set -euo pipefail`,
обрабатывают граничные случаи и завершаются кодами по соглашению
`sysexits.h`: 64 — неверные аргументы, 65 — некорректные данные, 69 — нет
зависимости, 77 — недостаточно прав.

### Цикл жизни пакетов (пункт 8 задания)

Прогнан на отдельной машине:

| Проверка | Результат |
|---|---|
| Установка | Проходит, каталоги с ключами получают права `drwx------ root:root` |
| Повторная установка поверх себя | Проходит без ошибок |
| `remove` | Конфигурационные файлы остаются — штатное поведение dpkg |
| `purge` | Снимок файловой системы совпал с состоянием до установки **до байта** |
| Коды возврата | `infra-ca-sign` без аргументов → 64, с неверным типом → 64 с внятным сообщением |

### Идемпотентность (пункт 3 рекомендаций)

Повторный запуск скриптов создания ресурсов ничего не пересоздаёт:

```
[INFO ] Сеть infra-net уже существует, пропускаю
[INFO ] Подсеть infra-subnet-a уже существует, пропускаю
[INFO ] Адрес ca-server-ip уже зарезервирован, пропускаю
```

`infra-ca-init` при повторном запуске сообщает, что корневой сертификат уже
выпущен, и ничего не перезаписывает: перевыпуск корня обесценил бы все ранее
выданные сертификаты.

## Известные исправления по ходу работы

Раздел оставлен намеренно: он показывает, что найдено и исправлено, а не
скрыто.

| Проблема | Причина | Исправление |
|---|---|---|
| `unknown property 'nat-ipversion'` | Опечатка в имени свойства | `nat-ip-version` |
| Квота статических адресов | Резервировалось три адреса при лимите два | Серверу мониторинга достаточно эфемерного |
| Правила групп безопасности отвергались | У `yc` требования к портам противоположны: `protocol=any` их требует, `protocol=icmp` запрещает | Раздельная обработка |
| Скрипты пытались создать существующее | `IFS=$'\n\t'` в библиотеке ломал разделение слов, и проверка существования всегда отвечала «нет» | Переопределение IFS убрано, защита от пробелов — кавычками |
| `unknown output format 'table'` | Флаг не поддерживается, табличный вывод и так по умолчанию | Убран |
| Конфликт файлов при установке | Пакет приносил чужой `/etc/default/prometheus-node-exporter` | Штатный drop-in для systemd |
| `Failed to update safessl-easyrsa.cnf` | Линковался только `easyrsa`, без `openssl-easyrsa.cnf` и `x509-types` | Линкуются все файлы Easy-RSA |
