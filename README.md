# Инфраструктура VPN-сервиса

Финальная работа по курсу «Старт в DevOps: системное администрирование для
начинающих». Облачный провайдер — Yandex Cloud, фаервол — firewalld.

---

## Задача

Компания консультирует по UI/UX-дизайну и быстро растёт. Большая часть
сотрудников работает удалённо, часто через публичный Wi-Fi. IT-инфраструктуры
нет: личные почтовые ящики, файлы вложениями к письмам, ссылки на Google Drive.

Требуется построить основу корпоративной инфраструктуры, где единственной
точкой входа во внутреннюю сеть служит VPN, а доступ выдаётся по сертификатам.
Помимо самого сервиса нужны мониторинг, резервное копирование и документация,
а разворачивание должно быть воспроизводимым.

---

## Архитектура

```
                          Интернет
                              │
                  1194/udp    │    22/tcp (только ADMIN_CIDR)
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
   ┌──────────────────────────────────────────────────┐
   │  VPC infra-net                                   │
   │                                                  │
   │  infra-subnet-a · ru-central1-a · 10.128.0.0/24  │
   │    ca-server   10.128.0.10   удостоверяющий центр│
   │    vpn-server  10.128.0.11   OpenVPN + NAT       │
   │    mon-server  10.128.0.12   Prometheus          │
   │                                                  │
   │  infra-subnet-b · ru-central1-b · 10.129.0.0/24  │
   │    backup-server 10.129.0.10  хранилище копий    │
   └──────────────────────────────────────────────────┘
```

Два принципа, на которых держится вся схема.

**Приватный ключ никогда не покидает машину владельца.** Сотрудник создаёт
ключ и запрос на сертификат у себя, присылает администратору только запрос,
а итоговую конфигурацию собирает локально. Компрометация удостоверяющего
центра поэтому не раскрывает ни одного клиентского ключа.

Схема отработана на практике: выпущен сертификат сервера, выдан доступ
клиенту, пройдена процедура отзыва и перевыпуска.

**Два независимых рубежа обороны.** Правила доступа заданы и в группах
безопасности облака, и в firewalld внутри каждой машины. Дублирование
намеренное: ошибка в одном слое не раскрывает сервер целиком.

## Структура репозитория

```
├── scripts/              скрипты развёртывания и обслуживания
│   ├── project.env       единственное место с адресами и именами
│   ├── lib/common.sh     общая библиотека для всех скриптов
│   ├── cloud/            создание сети, групп безопасности, ВМ
│   ├── ca/               удостоверяющий центр
│   ├── vpn/              VPN-сервер: ключ, запрос, настройка
│   ├── client/           машина сотрудника: запрос и сборка .ovpn
│   ├── admin/            оркестрация выдачи сертификатов
│   ├── monitoring/       развёртывание Prometheus и Alertmanager
│   └── test/             проверка состояния и пакетов на чистой ВМ
├── packages/             исходники deb-пакетов
├── dist/                 собранные пакеты
└── submissions/          отчёты и скриншоты по блокам
```

Пакеты по мере появления блоков:

| Пакет | Назначение | Блок |
|---|---|---|
| `infra-common` | библиотека `common.sh`, параметры `project.env` | 1 |
| `infra-hardening` | настройки SSH, параметры ядра, автообновления | 1 |
| `infra-ca-config` | команды `infra-ca-init`, `infra-ca-sign` | 1 |
| `infra-vpn-config` | конфигурация OpenVPN, `infra-vpn-make-client` | 2 |
| `infra-monitoring-config` | Prometheus, Alertmanager, 21 правило алертов | 3 |
| `infra-node-metrics` | node-exporter, метрики сроков сертификатов | 3 |

`infra-node-metrics` ставится на каждую машину инфраструктуры в момент её
создания. Метрики OpenVPN собирает `infra-openvpn-metrics` из пакета
`infra-vpn-config` — через тот же node-exporter, без отдельного порта.

## Сборка и проверка

```bash
# Сборка всех пакетов
cd packages
for p in */; do (cd "$p" && dpkg-buildpackage -us -uc -b --no-sign); done
mv ./*.deb ../dist/

# Соответствие Debian Policy
lintian dist/*.deb

# Качество скриптов
shellcheck -x -S warning scripts/*/*.sh packages/*/usr/sbin/*
```

Зависимости для сборки: `debhelper`, `devscripts`, `lintian`, `fakeroot`,
`shellcheck`.

---

## Замечание о `project.env`

Файл хранится в репозитории с безопасным значением `ADMIN_CIDR="0.0.0.0/0"`.
Реальный адрес администратора подставляется на рабочей машине перед запуском
скриптов и в репозиторий не попадает: публиковать свой домашний IP в открытом
доступе незачем.
